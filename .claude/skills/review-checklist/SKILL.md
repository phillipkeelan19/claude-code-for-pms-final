# Review checklist

Run the same four checks on any brief the user points at. They shouldn't have to explain the checklist again. If they haven't said which brief, ask for the file or pasted text in one short question. Read the whole brief before judging it.

## The four checks

1. **Owner.** The brief names who owns it, by person and role. Look for an "Owner", "From" or "DRI" line, or a named person responsible for delivery. A byline or author is not enough on its own: if it only says who wrote it, mark it as not met and say so.
2. **Success measure.** The brief says how we'll know it worked: a metric, a target or direction, and ideally a baseline and a date. "Improve the experience" is not a measure. If a measure is named but has no baseline, mark it partly met.
3. **Scope matches start to end.** Compare what the brief promises at the start (summary, goals, who it is for) with what the end delivers (scope, "what it does not do", next steps). Flag anything promised at the start that is missing at the end, anything at the end that was never introduced, and any "not in scope" item that contradicts the opening.
4. **Problem before fix.** The problem is explained, with evidence, before any solution is proposed. Flag a fix that appears first, a problem described only as the absence of the fix, and claims the brief states as fact without a source.

## How to report

Keep it short and the same shape every time:

**Verdict:** ready to go further / needs changes, in one line.

| Check | Result | Evidence |
| --- | --- | --- |
| Owner | Met / Partly / Not met | Quote or point to where in the brief |
| Success measure | Met / Partly / Not met | ... |
| Scope matches | Met / Partly / Not met | ... |
| Problem before fix | Met / Partly / Not met | ... |

Then a list of **fixes**, one line each, only for checks that are not fully met. Say exactly what to add or change, and where.

## Rules

- Judge only against these four checks. Mention other issues only in one closing line, if they are serious.
- Quote the brief for every result. Do not mark something met because it sounds plausible.
- Do not rewrite the brief unless the user asks. Do not edit the file.
- If the brief is a fictional Rook one, follow the project's CLAUDE.md as usual, including the hard rule on responder identities.
