What happened

Two changes shipped together. Nobody could see the harm.

On 12 Aug, 4.2 shifted the ranking weights and cut the ping wait from 90s to 60s. The rollout was clean, so everyone assumed it was fine. Priya and Marcus read the fallout as a seasonal August dip. The data says otherwise.

Module 3 · Rewind

Finding: misses are what separate the four from everyone else

Prompt 14 (verbatim)is the relation between the misses and the pings

Earlier in the same module, prompt 1 produced the four-responder trend: "show the statistics for the four reponders who did not get any pings, please show the trend and see if it matches to a ticket being raised by them".

FindingThe four missed 4+ pings in the first week after 4.2 (40–57% of their pings); everyone else missed 3 or fewer. Their not-taken pings were mostly misses, others' mostly turn-downs, yet the code penalises both at 0.12. Missed pings rose in every area and at every time of day, so a broad cause (probably the 60s wait) sits under the four-responder collapse. Callouts with no taker rose from 5.5% to 11.1%.

I matched finding to prompt by topic from the notes; the session logs don't pair them one-to-one.

Module 4 · X-Ray Vision

Finding: the code punishes a miss like a refusal, and gives no way back

Prompt 4 (verbatim)Find me the part of this code that takes points off somebody when they miss a ping or turn one down. Show it to me and explain it in plain English. Then find me every single thing in this code that puts points back on.
Prompt 5 (verbatim)A responder who has 0 would have to do what to get back to 0.5, walk me through it step by step
FindingOnly offer.py:28 adds points (+0.08, taken) and offer.py:30 removes them (−0.12, anything not taken). No decay, reset or override anywhere. From 0, a responder needs seven taken callouts in a row, and each miss undoes 1.5 of them. Because offers stop at the first yes, a low-ranked responder is only asked if everyone above declines, so "nobody is removed" is true only on paper.

Reading of the code, not Wen Li's stated intent. Assumes scores persist across deploys; unconfirmed.

The fix, shown not told

Make quiet responders visible, then give them a fair share of offers

Helen asked to see it from the point of view of the person it happens to before anyone changes code. Click around the prototype: the handler console flags Meteor Mite as quiet with a reason, and the phone view shows a "place in line" meter.

Detect

Console flags "available, but few offers since 4.2", before a ticket is needed.

Act

Handler acknowledges or tells Support in one click.

Recover

Low-ranked responders get a fair share of offers; a taken ping lifts them again. A weekly pings-per-responder view sits beside acceptance.

Prototype is 05-super-speed/prototype.html (keep this file beside the folder so it loads). Numbers are illustrative except Kip's two cards; responders' real scores aren't in the database. Showing responders a rating is still an open product decision: it could help them or invite gaming. The fix is my proposal, not agreed with Wen Li or Marcus Oyelaran.

Never again

4.2 wasn't a coding accident. It was a set of decisions that nobody had to defend in writing. The skill makes four questions unavoidable before any brief moves on.

Honest limits

It reviews briefs, not code. A weight change like 0.45 → 0.60 only gets checked if someone writes it into a brief with a success measure. Pair it with a rule that any routing-config change names the engineering manager and a per-responder metric.
